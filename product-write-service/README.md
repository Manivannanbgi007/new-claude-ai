# Product Write Service + CDC pipeline (MySQL → Debezium → Elasticsearch)

MySQL is the **single source of truth** for products. Elasticsearch is a **read/search projection**
that can be deleted and rebuilt at any time.

```
                        WRITE SIDE                                   READ SIDE
 POST/PUT/DELETE   ┌──────────────────────┐  binlog  ┌──────────┐  Kafka topic               ┌───────────────────┐
 ─── gateway ────► │ product-write-service│ ───────► │ Debezium │ ─ cdc.product_db.product ─►│ product-service    │
                   │  (port 8089)         │  MySQL   │ (Kafka   │   (compacted, key = id)    │  ProductCdcListener│
                   │  JPA + Flyway        │ product_ │ Connect) │                            │  ProductProjector  │
                   └──────────────────────┘   db     └──────────┘                            │        │           │
                                                                                             │        ▼           │
 GET  ───────────────────────── gateway ───────────────────────────────────────────────────► │  Elasticsearch     │
                                                                                             │  search API (8081) │
                                                                                             └───────────────────┘
```

| Component | Responsibility | Owns |
|---|---|---|
| **product-write-service** | Validate and commit product commands (create, update, delete) | MySQL `product_db.product` (container `mysql-product`) |
| **Debezium** (`kafka-connect`) | Read the MySQL binlog, publish every committed row change | Topic `cdc.product_db.product` |
| **product-service** | Project changes into the search document; serve search queries | Elasticsearch index `products` |

---

## 1. Why this design

**No dual write.** product-write-service only writes to MySQL. It never calls Kafka or Elasticsearch. When
the transaction commits, the change is in the binlog, and Debezium picks it up. There is no moment where
"MySQL has it but the search index missed it forever". If the read side is down, changes wait in Kafka.

**Debezium reads the binlog, not the tables.** It sees exactly the committed changes, in commit order,
without polling queries and without load on the application. Its position in the binlog is stored in
Kafka (`_connect_offsets`), so after a restart it continues exactly where it stopped.

**The read side owns the read model.** Debezium publishes rows as they are in MySQL (`ram_gb`, tags as
`"gaming,rtx"`, price as `"1099.00"`). `ProductDocumentMapper` in product-service is the **only** place that
turns a row into a search document (`ramGb`, tags as an array, `name.keyword`, normalizers). That separation
is what CQRS needs: the write model and the read model can evolve independently.

**Idempotent projection.** Every document stores the MySQL row `version`. The projector skips an event if
the index already holds that version or a newer one. Duplicate deliveries and replays are therefore
harmless.

**Avro through Confluent Schema Registry.** Debezium writes the change events as Avro (value) and registers
their schema under subject `cdc.product_db.product-value`. The registry's FULL_TRANSITIVE rule also protects
this topic: adding a nullable column is fine, while an incompatible table change makes the connector task
fail visibly instead of breaking consumers.

**The CDC topic is compacted** (key = product id). Kafka keeps at least the latest change per product, so
the whole index can be rebuilt from the topic (section 6).

**The CDC topic is internal to the product module.** It mirrors the table layout, which is an
implementation detail. Other services (order-service) will **not** consume it. In Phase B they get a
proper, versioned Avro event (`ProductSnapshot` on `product.catalog.v1`), so a column rename can never
break another team.

## 3. Setup

### 3.1 Infrastructure

The product module has its **own MySQL container**, `mysql-product` (host port **3308**), separate from the
shared `mysql` (3307) used by stock and order. On its first start it creates, from `.env`:

- database `product_db` and user `product_user` (`PRODUCT_DB_*`),
- Debezium's read-only user (`mysql-product/init/01-create-debezium-user.sql`).

```powershell
cd product-platform\infrastructure
docker compose up -d
docker compose up kafka-init          # creates the DLT topic (safe to re-run)
docker compose logs debezium-init     # connector registration result
```

`debezium-init` prints the status of connector `product-db-cdc`; expect `"state":"RUNNING"` for the
connector and its task.

**Check the binlog settings** Debezium needs:

```powershell
docker exec -it mysql-product mysql -uroot -pproduct_root_dev_password -e "SHOW VARIABLES WHERE Variable_name IN ('log_bin','binlog_format','binlog_row_image','server_id');"
```

Expect `log_bin = ON`, `binlog_format = ROW`, `binlog_row_image = FULL`, `server_id = 2`.

### 3.2 Remove the old search index (one time)

The old index holds documents with the old random ids and no `version`. In **Kibana → Dev Tools**:

```
DELETE products
```

product-service recreates it with the new mapping on startup, and Debezium's data fills it.

### 3.3 Build product-write-service

Generate a skeleton on start.spring.io (Boot 4.0.8, Maven, Java 21, YAML, Artifact `product-write-service`,
Package `com.example.productwrite`) with **Spring Web, Validation, Spring Data JPA, Flyway Migration, MySQL
Driver, Actuator, Eureka Discovery Client**, then copy the files over it.

### 3.4 Update product-service

Replace the project with the new version. It uses `spring-kafka` with an **explicit** configuration
(`config/KafkaConfig`, `@EnableKafka`) and Confluent's `KafkaAvroDeserializer`. The listener either starts,
and logs `partitions assigned`, or the application fails at startup; it can never be silently disabled.

### 3.5 Gateway routes

In `api-gateway/src/main/resources/application.yml`, add this route **above** the existing `product-service`
route:

```yaml
            # ---------------- Product WRITE side (CQRS commands) ----------------
            - id: product-write-service
              order: -1                         # evaluated before the read route
              uri: lb://product-write-service
              predicates:
                - Path=/api/v1/products/**
                - Method=POST,PUT,PATCH,DELETE
              # No Retry filter: writes must never be repeated automatically
```

The existing `product-service` route stays as it is. It now only receives `GET` requests, because every
write matches the route above first. Restart the gateway, and check that
`GET http://localhost:8080/actuator/gateway/routes` lists both routes.

## 4. Run

Start order:

1. `docker compose up -d` (MySQL, Kafka, Schema Registry, kafka-connect, Elasticsearch ...)
2. `eureka-server`
3. `product-write-service`: `.\mvnw.cmd clean spring-boot:run`
   - Flyway creates the `product` table.
   - **Sample products loaded into MySQL: 30 products**.
4. `product-service`: `.\mvnw.cmd clean spring-boot:run`
   - 30 × `Projected product id=... sku=... version=0`
5. `api-gateway`, then the other apps as before.

Step 3 can also run **before** product-service. The changes simply wait in Kafka, and product-service
projects them when it starts. That is the decoupling in action.

## 5. Verify the pipeline

Run `product-write-service/http/product-write-service.http` top to bottom. It creates, updates, and deletes
a product on the **write** side and checks the **read** side after each step.

What to look at while it runs:

| Where | What you see |
|---|---|
| **Kafka UI** http://localhost:8088 → Topics → `cdc.product_db.product` → Messages | One message per change, decoded from Avro, with `before`, `after`, and `op` (`r` snapshot, `c` create, `u` update, `d` delete) |
| **Kafka UI** → Schema Registry | Subject `cdc.product_db.product-value` (the Debezium envelope schema) |
| **Kafka UI** → Kafka Connect | `product-db-cdc`, RUNNING, with its config |
| **Kafka UI** → Consumers → `product-service` | Lag 0 when the projection is up to date |
| product-service console | `Projected product id=... version=1` |
| **Kibana** Dev Tools: `GET products/_doc/<id>` | The search document, with the same id and version as MySQL |

Compare the source of truth with the projection:

```powershell
docker exec -it mysql-product mysql -uproduct_user -pproduct_dev_password product_db -e "SELECT id, sku, price, version FROM product ORDER BY sku LIMIT 5;"
```

### Resilience tests (recommended)

**1. Read side down: no change is lost.**
Stop product-service. Create and update a product through the write service. Kafka UI shows consumer lag
growing. Start product-service: it catches up, and the lag returns to 0.

**2. Elasticsearch down: retry, don't skip.**
`docker compose stop elasticsearch`, then update a product. product-service logs retries with growing
delays (1 s, 2 s, 4 s ... up to 30 s). `docker compose start elasticsearch`, and the change is applied. Nothing
went to the DLT, and the order of changes is preserved.

**3. Debezium down: resumes from its binlog position.**
`docker compose stop kafka-connect`, then change products. `docker compose start kafka-connect`: Debezium
continues from its stored binlog position, and all changes arrive.

**4. Poison message: goes to the DLT, the pipeline keeps running.**

```powershell
docker exec -it kafka kafka-console-producer --bootstrap-server localhost:9092 --topic cdc.product_db.product --property parse.key=true --property key.separator=:
```

Type `bad-key:this is not avro` and press Enter, then Ctrl+C. product-service logs `Sending record to DLT`, and
Kafka UI shows the record in `cdc.product_db.product.product-service.dlt`, with headers describing the error
(`kafka_dlt-exception-message`, original topic, and offset). Further product changes still project normally.

## 6. Rebuild the whole search index

Because the index is a projection, you can throw it away, for example after changing the mapping:

```powershell
# 1. stop product-service
# 2. Kibana Dev Tools:  DELETE products
# 3. rewind the consumer group to the beginning of the (compacted) CDC topic:
docker exec -it kafka kafka-consumer-groups --bootstrap-server localhost:9092 --group product-service --reset-offsets --to-earliest --topic cdc.product_db.product --execute
# 4. start product-service -> it recreates the index and replays every product
```

Always rebuild from the **earliest** offset, so each product's deletes are replayed after its creates.

If the topic itself is ever lost, Debezium can re-snapshot MySQL. That's an advanced operation; the Debezium
docs describe it under "incremental snapshots" / signals.

## 7. Toward full CQRS

This step already has the CQRS structure:

| CQRS concept | Here |
|---|---|
| Command side | product-write-service: `ProductCommandService`, JPA entity, MySQL |
| Query side | product-service: `ProductSearchService`, Elasticsearch document |
| Synchronisation | Debezium CDC → `ProductProjector` (asynchronous, eventually consistent) |
| Separate models | `productwrite.model.Product` (table) vs `product.model.Product` (search document) |
| Routing | Gateway: writes → command side, reads → query side |

Later stages build on this without redesigning the flow:

- **More read models:** another projector (for example a recommendations index) consumes the same CDC topic.
  No change to the write side.
- **Domain events instead of row changes:** add an `outbox_event` table to product-write-service, written in
  the same transaction, and let Debezium's **Outbox Event Router** publish those events. The same
  infrastructure and pattern is used for `ProductSnapshot` in Phase B.
- **Command validation / business rules** grow in the write service only; queries stay fast and simple.

**Consequence to design for: eventual consistency.** After a `POST`, a `GET` through the gateway may return
404 for about a second, until the projection catches up. Clients should use the write response (it contains
the full product), or retry the read briefly. This is normal in CQRS and the reason `Location` + 201 is
returned with the full body.

## 8. Security considerations

- The **Debezium MySQL user is read-only**: it can read the binlog and data, but cannot change anything.
- Each service user sees only its own database (`product_user` → `product_db`).
- Kafka Connect's REST API (port 8083) can create and delete connectors: it is bound to `127.0.0.1` and must
  **never** be publicly reachable. In production, secure it and keep connector passwords in a secret store
  (Kafka Connect config providers) rather than in the JSON file.
- The write-side `GET /api/v1/products/{id}` is only reachable directly (port 8089); the gateway routes `GET`
  to the read side.

## 9. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `debezium-init` fails with connection refused | kafka-connect not ready yet | `docker compose up debezium-init` again |
| Connector task `FAILED`: `Access denied for user 'debezium'` | `mysql-product` volume existed before the init script was added | Reset `mysql-product` (see the platform setup notes), or create the user manually with the SQL in `mysql-product/init/` |
| Task `FAILED`: `Public Key Retrieval is not allowed` | MySQL 8 authentication without TLS | `database.allowPublicKeyRetrieval` must be `true` in the connector JSON; re-run `debezium-init` |
| Task `FAILED`: `The MySQL server is not configured to use a ROW binlog_format` | Binlog settings changed | Check the variables in section 3.1 |
| Topic `cdc.product_db.product` doesn't appear | No change captured yet, or `table.include.list` is wrong | Start product-write-service (sample data creates changes); check the connector config |
| product-service: `Topic cdc.product_db.product not present in metadata` | Topic not created yet | Start product-write-service once (Debezium creates the topic on the first change) |
| Read side stays at 0 products | Old consumer offsets, or the index was deleted while the service was running | Rebuild (section 6) |
| Search results have `"version": null` | Old documents from before this change | `DELETE products` and rebuild (section 6) |
| Changes stuck, lag grows, logs show retries | Elasticsearch unhealthy | Fix Elasticsearch; the projection resumes automatically |
| `Schema-validation: wrong column type` in product-write-service | Entity and migration disagree | Fix the entity or add a `V2__` migration; never edit `V1__` after it ran |
